What you see is not always what you sign

The largest multisig thefts of 2024 and 2025 had one thing in common: the signers approved transactions that did not do what their screen described. Together they cost well over a billion dollars. They followed three patterns.

The disguised delegatecall

A transfer on the surface, a takeover underneath.

The screen said

A routine transfer between the team's own wallets.

The signature approved

A delegatecall that hands the Safe's logic to another contract.

operation = 1 (delegatecall)

Safe Tx Lens flags the delegatecall and the unverified target contract before anyone signs.

The silent upgrade

An ordinary approval that swaps the code behind the wallet.

The screen said

An ordinary transaction, ready to approve.

The signature approved

A call that replaces the contract behind the Safe.

upgrade → new implementation

Safe Tx Lens decodes the calldata itself, says plainly that the call swaps the implementation, and checks the new code.

The ownership handover

Routine on screen and in simulation, final onchain.

The screen said

Routine transactions that matched their simulations.

The signature approved

Calls that hand ownership of the protocol's contracts to someone else.

transferOwnership(new owner)

Safe Tx Lens reads the raw data independently of the signing interface and names the new owner.

Patterns drawn from public post-mortems; the figure is checked against them before launch. A review is one more pair of eyes. It cannot promise to catch every attack, and the hash on your signing device remains the last check.

Start with anything you have

Exported transaction JSON can be decoded without a Safe API key. An execution hash needs a working RPC; a pending Safe hash needs a proposal source.

How it works

One review connects the source of the transaction, a fresh Safe hash calculation, decoded calls, target code, and measured effects when available.

Every claim shows its source
  1. Your inputSafe transaction hash

    A hash alone contains no chain ID, Safe address, or calldata.

  2. Recover fieldsOffchain proposal source

    Safe Transaction Service supplies the transaction if it has indexed it. A pending hash needs a proposal source.

  3. Our checkRecalculate and compare

    Compute EIP-712 locally from those fields. When available, ask the Safe contract through RPC for its hash.

  4. ReviewCalls, code, effects

    Decode nested calls; check target code and show simulation changes only when measured.

If Safe supplies both the fields and the reference hash, a matching hash proves consistency, not that Safe supplied truthful fields. Compare the hash shown on your signing device.

  1. Your inputOnchain execution hash

    Select a network if the hash alone cannot identify it.

  2. Recover fieldsRPC execution and calldata

    Read the transaction, receipt, and Safe execution event from the chain; reconstruct the Safe transaction.

  3. Our checkRecalculate and compare

    Compute EIP-712 locally and compare the event hash. Query the Safe contract at the earlier block when archive state exists.

  4. ReviewCalls, code, effects

    Decode calls and inspect code at execution time where the RPC and verified source allow it.

This path does not need Safe Transaction Service to reconstruct an executed transaction. Its independence depends on the RPC you trust; historical checks need archive state.

  1. Your inputSafe address or URL

    A Safe URL supplies the chain. An address alone can exist on several chains.

  2. Find transactionsQueue and history

    Where supported, Safe Transaction Service lists proposals and executions. Choose one transaction.

  3. Our checkRecalculate each selected hash

    Read its full fields, compute EIP-712 locally, and attempt the separate Safe contract RPC check.

  4. ReviewCalls, code, effects

    Show the decoded call path and the evidence still missing for that transaction.

A Safe address is a discovery input, not proof of what was signed. If the offchain queue is unavailable, this service cannot invent pending proposals from RPC.

  1. Your inputTransaction JSON

    Use a complete Safe export, including the Safe, chain, nonce, and transaction fields.

  2. Recover fieldsYour file, parsed as data

    Those fields do not need Safe Transaction Service. A Builder plan without a nonce is shown as a plan.

  3. Our checkRecalculate EIP-712

    Compute the Safe hash without calling Safe Transaction Service. Compare a separately supplied reference hash and, where possible, the Safe contract via RPC.

  4. ReviewCalls, code, effects

    Decode nested calls and mark code checks or simulation as unavailable when they cannot run.

An imported file can itself be wrong. Check its origin and compare the calculated hash with your signing device before approving anything.

The security boundary

Hash calculation is independent of the Safe API; the truth of input fields is a separate question. A compromised Safe service could return altered fields and a matching hash. Use a hash obtained independently, your signing device, and onchain evidence where available. No single service or simulation proves a transaction is safe.

Use it your way

The same analysis runs in the browser, inside your AI assistant, from the command line, or on your own machine.

Add the community endpoint to any MCP client that supports Streamable HTTP. It exposes read-only tools and shares the web quota. It does not run arbitrary URLs or accept your RPC endpoint.

  • inspect
  • inspect_json
  • list_pending
  • list_history

Read the MCP guide

codex mcp add safe-tx-lens --url https://safetxlens.org/mcp

Other clients: add https://safetxlens.org/mcp as a Streamable HTTP server in that client's own settings.

The CLI uses the same analysis as the website. Add --json for machine-readable output, or point it at a Safe address to list its queue and history.

Needs Node.js 20 or newer.

git clone https://github.com/rriescog/safe-tx-lens.git
cd safe-tx-lens && npm ci
node bin/safe-tx-lens.mjs inspect 0xSAFE_TRANSACTION_HASH --network auto

What this service keeps about you

It needs no account and sets no cookies. To keep the free service available to everyone it enforces usage limits, and this is everything that involves.

Never stored

  • The hashes, addresses, links or JSON you inspect
  • Reports, which are built for your browser only
  • Cookies, accounts or per-request logs

Held in memory until the UTC day ends

  • A salted hash of your IP address, used only to apply the daily request limit
  • It is never written to disk and is gone when the service restarts

Written to disk

  • Total usage counters for the day and the month, with nothing that identifies a visitor

Error reports contain a random reference, a time, a category and a status code; no input, address or IP. You can read all of it in the source code, or run your own copy.

Use the evidence, verify independently

Safe Tx Lens is an independent community project, not affiliated with or endorsed by Safe or the Safe Ecosystem Foundation. It is free software with MIT-licensed source available on GitHub. Its data and analysis can be incomplete, outdated, or incorrect. It offers no guarantee that a transaction is safe and its maintainers accept no responsibility for decisions made from its output. Check the hash on your signing device, use independent sources, and review the contract behavior yourself.

For control over the code, keys, RPCs, and logs, deploy your own instance. If you find an error, report it on GitHub with public, non-sensitive details.
