# Community service deployment

The hosted service serves the same read-only Safe lookup and decoding workflow as the local app. A visitor can enter a previously unseen queued Safe transaction hash, executed hash, Safe URL, Safe address, or JSON. Safe Transaction Service is the primary proposal source. Network auto-detection checks supported chains; an address on multiple chains requires the visitor to choose one.

The web UI and hosted `/mcp` endpoint share one persistent daily/monthly unit budget and per-IP daily request count. Default reservations are 600 units/day, 10,000/month, and 20 requests/day/IP; an automatic cross-chain lookup costs more than a JSON decode. This is a conservative estimate of upstream work, **not** an exact Safe API counter. HTTP 429 returns `Retry-After` and a wait time. One request runs at a time. The IP is salted and held only in memory for that day; quota files contain aggregate counters. Restarting the app resets the per-IP counters. Run one app replica; multiple replicas would need a shared atomic quota store.

Optional Tenderly simulation is invoked only for one selected transaction through the web UI or MCP. It requires credentials and a project dedicated to this service. If not configured, the public interface says simulation is unavailable. If configured, it permits up to three simulation requests/day/IP and 100/month globally by default, in addition to the shared request budget. Set `COMMUNITY_SIMULATION_CLIENT_DAILY` and `COMMUNITY_SIMULATION_MONTHLY` in the Compose environment to change these limits. The per-IP allowance is held in process memory and resets on a restart; the global monthly cap persists in the quota volume. These are ceilings, not a promise of three simulations to each visitor: the shared budget or Tenderly plan can be exhausted first. A simulation sends calldata and signatures to Tenderly, and results describe one execution path at one chain state.

## Provision

1. Prepare a Linux VPS with Docker Engine and Compose, inbound 80/443, and a non-root deploy user with Docker permission. Point the `safetxlens.org` apex A record to the VPS IPv4 address; add an AAAA record only if the VPS serves IPv6. Confirm DNS and TLS before enabling deployment to a new host.
2. Create a dedicated Safe Builder API key for this service. On the VPS, place its value in `~/safe-tx-lens/safe-api-key` with permissions `0600`; this file is mounted as a Docker secret and is never copied from the repository or put into GitHub Actions logs.
3. Set repository variables `DEPLOY_DOMAIN=safetxlens.org`, `DEPLOY_HOST`, and `DEPLOY_USER`, plus secrets `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`, and `GHCR_READ_TOKEN`. Set `DEPLOY_ENABLED=true` only after the VPS, DNS, and dedicated key are ready. CI refuses a different deployment domain.
4. To enable simulation, create a dedicated community Tenderly project and put its access key in `~/safe-tx-lens/tenderly-access-key` with permissions `0600`. Set repository variables `DEPLOY_TENDERLY_ENABLED=true`, `DEPLOY_TENDERLY_ACCOUNT`, and `DEPLOY_TENDERLY_PROJECT`. CI then includes `compose.tenderly.yaml` on each deployment. The default Compose file leaves Tenderly off.
5. To enable Etherscan V2 ABI lookup across its supported chains, including Polygon PoS (`chainid=137`) and Amoy (`chainid=80002`), put a dedicated Etherscan key in `~/safe-tx-lens/etherscan-api-key` with permissions `0600` and set `DEPLOY_ETHERSCAN_ENABLED=true`. To enable OKLink ABI lookup for X Layer, put its dedicated key in `~/safe-tx-lens/oklink-api-key` with permissions `0600` and set `DEPLOY_OKLINK_ENABLED=true`. These optional files are mounted as Docker secrets; GitHub stores only the enable flags. Without them, Sourcify and supported keyless explorer routes remain available, but Etherscan and authenticated OKLink lookup are not active. Do not enable a flag until its file exists on the VPS.

The `quality` workflow checks every PR with tests, a dependency audit, and Compose validation. After a change reaches `main`, the build-and-deploy workflow repeats those gates and publishes an immutable GHCR image. With deployment enabled, CI copies the Compose/Caddy configuration and starts that digest behind automatic HTTPS. It checks that the Safe key file already exists; the deployment never creates or overwrites it. Caddy overwrites `X-Client-IP` with the actual connecting IP, and the app container has no public port. `/mcp` permits only read-only lookup tools and uses the same quota gate as `/api/inspect`; it exposes no caller-supplied RPC URL or polling control. An explicit single-transaction simulation is available through either endpoint only when the separate Tenderly secret and deployment variables are configured. The simulation has additional per-IP and monthly limits.

After deployment, check `https://safetxlens.org/healthz`, a previously unseen queued Safe hash, a Safe queue, and one MCP `tools/list` at `https://safetxlens.org/mcp`. For rollback, set `IMAGE` in `~/safe-tx-lens/.env` to a previous digest and run `docker compose --env-file .env -f compose.yaml up -d`.

The app limits JSON bodies to 256 KiB and has a 15-second request timeout. The public interface has no 30-second watch control. User-supplied URLs must use `https://app.safe.global` with no credentials; they are parsed for a Safe address and optional transaction hash, never fetched by the server. Hashes, addresses and JSON remain supported inputs and cannot select an outbound host. The Safe API, RPC, Sourcify and optional Tenderly remain external trust boundaries; a matching hash proves consistency of fields, not benign contract behavior.

Unexpected failures and missing routes return a user-facing incident reference. The app writes a small JSON event to stderr with its ID, time, category, and status; transaction input, URL, IP, and credentials are excluded. Compose rotates container logs at 10 MiB with three files. Operators can look up a reported reference with `docker compose -f compose.yaml logs app | grep <reference>`; no automatic external notification is configured.

## RPC coverage and production limits

The community container uses the public RPC defaults in `src/onchain.mjs` and rejects `RPC_URL` and `RPC_URL_<NETWORK>` in its environment. Adding a private endpoint to the VPS environment will **not** activate it. Public RPC availability therefore remains a dependency. Historical bytecode and storage checks require an RPC that serves the inspected block. See [configuration](../docs/CONFIGURATION.md) and [network coverage](../docs/NETWORK-COVERAGE.md).
